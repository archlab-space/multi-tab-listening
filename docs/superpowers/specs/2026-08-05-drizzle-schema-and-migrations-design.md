# Drizzle Schema, Migrations, and Database Startup — Design

- **Date:** 2026-08-05
- **Status:** Approved, ready for implementation planning

## Goal

Move the database schema out of `discord-monitor`, put it under versioned
migrations, and make it the single source of the row types the services
already hand-write. Reduce a new machine's database setup to two commands.

## Problem

Three separate problems that share one cause — the schema has no owner.

**The schema lives inside a service that is not its owner.**
`discord-monitor/src/setup-database.ts` creates every table in the workspace:
`channels`, `messages` and `threads` (which it does own), plus `tweets` (written
by tweet-generator, drained by x-poster) and `generation_attempts`
(tweet-generator only). Worse, `discord-monitor/src/index.ts:24` calls
`setupDatabase()` on every startup, so running the tweet generator requires
first running — or at least invoking a script belonging to — an unrelated
service that opens browser tabs onto Discord.

**Schema changes have no version.** `setup-database.ts:89` already carries two
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements appended after the fact,
with a comment explaining why they cannot be folded into the `CREATE TABLE`
above: `CREATE TABLE IF NOT EXISTS` is a no-op against an existing database.
Every future column adds another such patch, and nothing records which
statements a given database has actually seen.

**The row types are a hand-maintained copy.** `shared/src/types.ts` opens by
admitting it: "These mirror the schema created in
discord-monitor/src/setup-database.ts". Three interfaces, 83 lines, kept in
sync by hand. `x-poster/src/queue/tweet-queue.ts:25-39` then maps snake_case
rows onto them field by field — a second hand-maintained copy of the same
column list, and one where omitting a field is silent.

## Non-Goals

- Containerising the four services. They keep running as local processes
  started by hand; a server deployment is a possible future, not this work.
- Changing any query's behaviour. This is a rewrite of how queries are
  expressed, not of what they do.
- Down migrations as an operational tool. They are generated because
  drizzle-kit generates them; recovery in practice is roll-forward.
- Exposing Drizzle Studio anywhere but localhost.

## Decision

Drizzle ORM, used fully: schema defined in TypeScript, migrations generated
from it, and every runtime query rewritten against it.

### Why not the alternatives

**Hand-written migration runner + raw SQL.** Fits the repo's existing style
(no ORM, plain `pg`, thick comments) and adds no dependency, but leaves the
row types hand-written and the snake_case mapping hand-written. It solves the
ownership and versioning problems and neither of the type problems.

**node-pg-migrate.** Supports plain `.sql` migrations natively and accepts a
pg config object where `loadDbConfig()` already produces one, so it fits
cleanly. But it generates no types — in either its SQL or its `pgm.createTable`
DSL mode. It is a migration runner, not a schema-to-type tool. Choosing its
DSL buys nothing on types, and for this schema would produce a mixture: the
`GIN(to_tsvector('english', content))` index needs a raw-SQL escape either way,
so half the file would be DSL and half SQL — less readable than uniform SQL.

**node-pg-migrate + kysely-codegen.** Types generated by introspecting the live
database, migrations stay raw SQL. Works, and keeps the schema in SQL where it
can be pasted into psql. Rejected because it needs a standing human discipline
— "after changing a migration, regenerate the types" — that nothing enforces.

**Drizzle Kit only, keeping raw `pg` for queries.** Considered and rejected in
favour of the full adoption. It delivers types, generated migrations, and
Studio without touching a single query, but the snake_case-to-camelCase mapper
survives, because raw `pg` returns the database's column names while
`$inferSelect` returns the names declared in the schema. Eliminating that
mapper was the point.

### What Drizzle gives that the others do not

- **One definition, types derived.** `typeof tweets.$inferSelect` replaces the
  hand-written `Tweet` interface. A column added to the schema appears in the
  type; a column removed breaks compilation at every use.
- **No mapping layer.** Drizzle returns objects keyed by the schema's field
  names, so `toTweet()` and its equivalents are deleted rather than typed.
- **Studio.** `drizzle-kit studio` browses and edits rows in a browser using
  the existing config. Not unique to Drizzle — any GUI client does this — but
  it needs no second set of credentials.
- **`drizzle-kit pull`** introspects the current database into a schema file,
  so the starting point is generated from what actually exists rather than
  transcribed from `setup-database.ts` by hand.
- **pgvector is native**: `vector({ dimensions: 1536 })`, no custom type
  wrapper for the `embedding` column.

## Architecture

```
shared/src/schema.ts      Drizzle pgTable definitions — the source of truth
shared/src/types.ts       Types inferred from schema + the few hand-written ones
db/
  drizzle.config.ts       Points at ../shared/src/schema.ts
  migrations/             drizzle-kit generate output, committed
  package.json            scripts: generate / migrate / studio
```

**The schema lives in `shared`, not in `db`,** because it is the contract
between the services — which is what `shared/src/types.ts` has always said it
is. Types must be derivable from it, so it has to sit where all four services
already import from.

**`db` holds only tooling:** drizzle-kit, the generated migrations, the Studio
entry point. No service depends on it at runtime.

`drizzle-orm` becomes a dependency of `shared`, so it appears in every
service's `node_modules`. The services import only types from it, which are
erased at compile time, so the runtime cost is zero.

### Type layers

```ts
// Derived — changes with the schema
export type Tweet = typeof tweets.$inferSelect
export type NewTweet = typeof tweets.$inferInsert
export type DiscordMessage = typeof messages.$inferSelect

// Hand-written — no table corresponds to it
export interface DiscordMessageWithChannel extends DiscordMessage {
  channelName: string | undefined
  guildName: string | undefined
}
```

`TweetStatus` and `TweetArchetype` are absorbed into the schema as column-level
enums (`varchar('status', { enum: [...] })`), so the union types are inferred
rather than maintained alongside. The exact syntax is confirmed during
implementation.

`DiscordMessageWithChannel` stays hand-written: it is the shape of a LEFT JOIN,
and the `undefined` on its two fields is a deliberate statement that the join
may not match — information no table carries.

## Query rewrite

Four files, ~930 lines. Most of the conversion is mechanical. These are the
places Drizzle cannot express directly and an `sql` template is used:

| Location | Current SQL | Drizzle |
|---|---|---|
| `x-poster/.../tweet-queue.ts:98` | `FOR UPDATE SKIP LOCKED` | `.for('update', { skipLocked: true })` |
| `x-poster/.../tweet-queue.ts:93` | `attempts = attempts + 1` | `` sql`${tweets.attempts} + 1` `` |
| `x-poster/.../tweet-queue.ts:167` | `COUNT(*) FILTER (WHERE ...)` | `` sql`count(*) filter (where ...)` `` |
| `x-poster/.../tweet-queue.ts:68` | `COALESCE($7, NOW())` | `` sql`coalesce(...)` `` |
| `ai-assistant/.../queries.ts:248` | `ts_rank(to_tsvector(...), plainto_tsquery(...))` | full `sql` template |
| all four files | `ON CONFLICT ... DO NOTHING/UPDATE` | `.onConflictDoNothing()` / `.onConflictDoUpdate()` |

What is hand-written changes from *mappings* to *expressions*. The distinction
matters: an `sql` template used inside `.select({ ... })` still yields a typed
result, whereas a mapping function that omits a field compiles today and fails
at runtime.

## Sequencing — tests before the rewrite

Half the code being rewritten has no test coverage:

| File | Lines | Tests |
|---|---|---|
| `x-poster/src/queue/tweet-queue.ts` | 179 | yes — 17, against a real database |
| `tweet-generator/src/store.ts` | 166 | yes — against a real database |
| `ai-assistant/src/database/queries.ts` | 439 | **none** — the package has no `test` script |
| `discord-monitor/src/database.ts` | 148 | **none** |

The largest file has no safety net and contains the hardest query to convert.

**Characterization tests come first.** Before any Drizzle rewrite,
`ai-assistant/src/database/queries.ts` and `discord-monitor/src/database.ts`
get tests against a real database that record what the current code *does*,
not what it ought to do. `ai-assistant` gains a `test` script and a vitest
config to host them.

This is the right tool for the situation: the work is a behaviour-preserving
rewrite, and the full-text search logic in particular cannot be verified as
equivalent by reading it.

## Database startup

Root `package.json` gains scripts, keeping `pnpm` as the single entry point:

```bash
pnpm db:up        # docker compose up -d, wait for healthy, run migrations
pnpm db:migrate   # migrations only
pnpm db:studio    # open Drizzle Studio
pnpm db:reset     # down -v, up, migrate — local do-over
pnpm db:down      # stop the container
```

`docker-compose.yml` gains a `healthcheck` (`pg_isready`) on the postgres
service, and `db:up` runs `docker compose up -d --wait`, which blocks until
that healthcheck passes. Waiting on a declared state rather than guessing with
`sleep` is the whole reason the healthcheck is added. The obsolete
`version: '3.8'` line is removed — current Docker warns on it.

A new machine becomes:

```bash
pnpm install
pnpm db:up
```

## Migration path

The local database is wiped and rebuilt; there is no data worth preserving.

1. `drizzle-kit pull` against the current database to generate the initial
   `shared/src/schema.ts`. The live database is the authority on what the
   schema is — not `setup-database.ts`, which has drifted before.
2. Review the pulled schema by hand: restore the explanatory comments from
   `setup-database.ts` (the TIMESTAMPTZ rationale, the `uncertain` status,
   the dedupe key's role), and add the column-level enums.
3. `drizzle-kit generate` to produce the baseline migration.
4. `docker compose down -v`, then `pnpm db:up`, and verify the schema built
   from migrations matches what was pulled.

## Deletions

- `discord-monitor/src/setup-database.ts`
- `await setupDatabase()` at `discord-monitor/src/index.ts:24` — a service must
  not alter the schema on startup, least of all three other services' tables
- the `setup-db` script in `discord-monitor/package.json`
- the field-by-field row mappings: `toTweet()` at
  `x-poster/src/queue/tweet-queue.ts:25`, and the inline equivalents at
  `ai-assistant/src/database/queries.ts:38` and
  `discord-monitor/src/database.ts:100`. `tweet-generator/src/store.ts` has no
  mapping function — it reads single columns off rows directly
  (`row.dedupe_key`, `row.external_id`), which Drizzle replaces with typed
  field access rather than deletes.
- the hand-written `Tweet` and `DiscordMessage` interfaces in
  `shared/src/types.ts`

`README.md` and `discord-monitor/README.md` both document
`pnpm --filter discord-monitor run setup-db` and are updated to `pnpm db:up`.

## Phases

One plan, but strictly ordered — each phase leaves the workspace green:

1. **Characterization tests** for `ai-assistant/src/database/queries.ts` and
   `discord-monitor/src/database.ts`, against the current code.
2. **Schema and migrations**: `db` package, `shared/src/schema.ts`, baseline
   migration, `pnpm db:*` scripts, compose healthcheck. Delete
   `setup-database.ts` and its startup call.
3. **Query rewrite**, one file at a time, its suite green before the next:
   `tweet-queue.ts` → `store.ts` → `database.ts` → `queries.ts`. Covered files
   first, so the mechanics are settled before reaching the 439-line one.
4. **Type cleanup**: hand-written interfaces in `shared/src/types.ts` replaced
   by inferred ones once nothing consumes the old shapes.

## Verification

- Every existing test passes unchanged. The 313 currently passing are the
  contract: this work changes how queries are written, not what they return.
- The characterization tests written for `queries.ts` and `database.ts` pass
  both before and after their file's rewrite. A test that only passes after
  is not a characterization test.
- A database built from migrations alone, starting from `down -v`, serves
  every existing test.
- `tsc` passes in all four packages.
- `pnpm db:up` on a machine with no container running reaches a migrated
  database without manual intervention.

## Risks

**The rewrite is large and behaviour-preserving, which is the kind that hides
regressions.** Mitigated by tests first, and by rewriting one file at a time
with its suite green before moving on.

**`drizzle-kit pull` may not reproduce the expression index.**
`idx_messages_content_fts` uses `GIN(to_tsvector('english', content))`. If the
pull drops or mangles it, it is written by hand into the baseline migration and
verified with `\d messages`.

**Studio connects with full credentials and no permission layer**, by its own
documentation. It stays bound to localhost and is never run on a server.
